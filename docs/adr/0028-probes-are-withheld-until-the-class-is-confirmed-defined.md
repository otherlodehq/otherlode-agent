# A class's probes stay out of the manifest until the class is confirmed defined

`ProbeRegistry.register` commits from `AgentBuilder.Listener.onTransformation`, which ByteBuddy calls only once `make()` has produced the class's bytes. ADR 0007 put it there to close the window where a transform failed after the probes had been computed. Three failures happen after that point and it cannot see any of them: the verifier can reject the woven class, a transformer registered later in the chain can replace the bytes, and `defineClass` can raise a `LinkageError` for a supertype that is absent at load. In the first and third the class is never defined at all, yet the registry holds its probes, the manifest carries them, and nothing ever increments them. Permanently zero is what a collector reads as dead code, which is the outcome ADR 0007 exists to rule out.

A class's probes are therefore withheld from the manifest until the agent has confirmed the class was defined. Confirmation has two sources. A non-zero count is proof on its own: a probe increments only through the array the registry handed that class's initializer, so a count above zero means the woven class was defined and ran. For a class whose counts are all zero, the agent looks for it in `Instrumentation.getAllLoadedClasses()`. A class absent from that set on two consecutive sweeps is withheld for good and named in a `WARNING`; a class whose classloader has since been collected is published rather than withheld, since a collected loader is the absence of evidence rather than evidence of absence. Nothing is published about a class that failed, so nothing has to be taken back, and no wire field is added: a class that was never defined never loaded, so a collector diffing the static baseline against the manifest reaches a claim that is true.

The scope is the two failures that leave the class undefined. A later transformer replacing the bytes leaves the class defined and running with its probes gone, which no comparison against the loaded set can see, and the one signal that would separate it from a class that simply was never initialised is reading the loaded class's declared fields for `$otherlodeProbeCounts`. `Class.getDeclaredFields()` resolves every field's type: on JDK 22 a field type that `findLoadedClass` reported as absent was loaded by the call itself. A detector that manufactures class loads corrupts the data it reports on, so that failure stays a recorded gap.

## Considered options

- Detecting the failure after the fact and retracting the class's rows. Rejected: the probes are already on the wire and may already have been delivered, and the schema has no tombstone, a gap ADR 0027 noted and got away with only because an unreported class had no prior rows to contradict. Confirming before publishing removes the problem instead of building machinery to undo it, and it costs one `continue` in `computeManifestDeltas`, which already stages and commits classes one at a time.
- A bucket on `ProbeManifest` beside `unreported_classes`, naming each class that was woven and never defined. Deferred rather than rejected. "Never loaded because nothing referenced it" and "never loaded because loading it failed" are different findings, the first dead code to delete and the second a deployment to fix, and only the agent can tell them apart. But that is a new capability rather than a correction of a wrong claim, and it costs a proto field, a registry bucket, a chunk weight, codec work and a collector change for a population nobody has yet shown exists. `STATUS.md` carries it, to be built when a report from a real service shows these classes turning up.
- JFR's `jdk.ClassDefine` as a positive per-class definition signal, with `jdk.ClassUnload` answering the collected-loader question exactly. Rejected: both event types exist on JDK 22 and both are disabled by default, so using them means the agent starting a recording inside the target JVM, a larger imposition than anything else this agent does, and unavailable when the adopter is already driving JFR themselves.
- Reflective `ClassLoader.findLoadedClass` to ask about one class instead of walking every loaded class. Rejected: it needs a classloader reference the registry does not keep, since `RegistryKey` holds only `System.identityHashCode`, and `--add-opens` on `java.base`.
- A time-based grace period, holding a class's probes for a fixed interval after registration and publishing regardless. Rejected: it delays publication without detecting anything, so a class that never defined is published on schedule exactly as it is today.
- Extending the same treatment to the endpoint tier in this round. Deferred, with the reason recorded rather than left to omission. `EndpointInstrumentation` stages and commits declarations from its own listener for the ADR 0007 reason, so a class that declares endpoints and then fails to define leaves rows that read as never called. The exposure is narrower than the probe tier's: the probe tier registers every class the agent weaves, while `JaxRsModule` is the only module that declares from inside a transform, and every other module declares at runtime from a framework object that already exists. `PendingDeclarations` stages opaque closures with no class identity, so the link is `begin()` taking the declaring class name and `commit()` attaching it. `EndpointEntry.handlerClass` happens to hold the same string for JAX-RS but is a display label, nullable and set at dispatch for other modules, so it is the wrong thing to read as a structural link.

## Consequences

- The grace period is the flush cadence rather than a constant someone has to defend. Registration commits inside `transform()` and the JVM defines the class as soon as the transformer chain returns, so confirmation lands microseconds later while the first manifest is up to a flush interval away. In the ordinary case a class is confirmed before it would first have been sent, and withholding changes nothing about when it is published.
- Each registry entry keeps a `WeakReference` to the classloader. A cleared reference means the loader was collected, so the class is published rather than withheld: a loader created, used and collected inside one flush interval is ordinary for a script engine or a per-test loader, and withholding there would lose a class that ran. A class registered against the bootstrap loader has no reference to clear and the bootstrap loader is never collected, so absence from the loaded set is real evidence for it.
- Only a class whose counts are all zero needs the loaded-set check, and when there is no such class the walk is skipped entirely.
- One sweep serves both directions, renamed `LoadedClassSweep`. It takes the loaded array once per flush and answers the reverse direction from a name set; ADR 0027's forward direction keeps its per-class filter and its every-tenth-flush cadence, which is the expensive part. Two comparisons with opposite race properties then sit in one place, where the next reader meets both at once.
- One `WARNING` per withheld class, uncapped, and a summary count on the shutdown flush. The log is the only output this decision produces, so the class name in it is the deliverable. The population is bounded by classes the agent wove that never defined, which should be none; a large one means the adopter's deployment is broken and the volume is proportionate to that rather than noise about it.
- No configuration flag, for the reason ADR 0027 gave the sweep interval: turning it off restores the wrong claim it exists to prevent, and there is nothing to tune.
- Delta batches are unaffected. A class with all-zero counts produces no delta rows, and a class confirmed by a non-zero count has its manifest row computed in the same flush, which is the ordering that already holds for a class registered between two flushes.
- Confirmation matches on the class name alone, the identity `skipped_classes` and every other table the collector joins on already use, so a class is confirmed when any classloader anywhere in the JVM has defined something of that name. An entry registered under one loader that failed to define is therefore confirmed by a live namesake under another. That errs in the safe direction twice over: withholding is the claim that needs evidence, and a collector keying on the same name sees the live copy's hits beside the failed copy's zeros, so no dead-code claim follows from it. Telling the two apart would mean carrying a classloader identity onto the wire, which nothing downstream has a concept of.
- Building the end-to-end proof turned up the same property in the test harness, sharply enough to be worth recording. Gradle's JUnit Platform discovery loads every compiled class under the test source set through the real application classloader, before any test method runs, to check it for annotations. A fixture class on disk is therefore already in `getAllLoadedClasses()` by the time a test's own sweep looks, whatever that test's own loader did, so the fixtures are generated bytecode that never exists as a `.class` file. The symptom was specific: the withheld case passed when the class ran alone and failed only under the full build.
- A verifier rejection of the agent's own woven bytes is not tested. It takes the same path from registration onward as a `LinkageError` at definition, which is reproducible with a classloader defining a class whose supertype is absent, and staging genuinely unverifiable bytes would test the fixture rather than the code.

## Amended on 2026-10-06: the bucket is built

The deferred bucket on `ProbeManifest` is built, as `failed_classes` (ADR 0065). Collector ADR 0005 made a field added after release cost a stripped run, so it went in before `0.1.0`. Everything else here stands.

## Amended on 2026-10-06: a miss counts only once the definition attempt has ended

ADR 0066 replaces "absent on two consecutive sweeps" with "absent on two sweeps after the attempt to define the class ended", and clears a failure on a retry or a later confirmation. It also corrects this ADR: a class the verifier rejects is defined, since the JVM verifies after it defines, so it is confirmed and never withheld.
