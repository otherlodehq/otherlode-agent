# Branch sites the adopter did not write get no probe: inlined copies from out-of-scope code and coroutine machinery are dropped, in-scope inlined copies are kept and labelled

The branch tier probes every conditional jump and switch in a method. Two kinds of site are in the bytecode of the adopter's method without being the adopter's code. kotlinc copies the body of an `inline` function into each caller, so a call to `map`, `firstOrNull` or Ktor's `respond` brings that library's own jumps into the caller's method, attributed to the caller at a line number past the end of its file. And a suspend function or suspend lambda carries a state machine: a switch on the continuation's `label` whose default case only throws, a compare against `COROUTINE_SUSPENDED` after each suspension point, and an `instanceof` plus a re-entry test in the preamble. Measured over the compiled classes of this repo, its demos and a Ktor application: inlined library code is 16 to 25 percent of all branch sites in plain Kotlin, and in the Ktor application 46 of 51 sites were one of these two kinds. Both kinds read as never hit for reasons that say nothing about the adopter's program (a size check inside `map` always takes one side; a `label` default case cannot fire), which is the "confident and wrong" finding this project exists to avoid.

Those sites get no probe. An inlined copy is recognised from the class's `SourceDebugExtension` (the JSR-045 SMAP kotlinc writes, `Kotlin` stratum), which maps each output line to a source file and the internal name of the class that declares the inline function. A copy whose origin class is outside the include and exclude rules is dropped. A copy whose origin class is in scope is kept, since it is the adopter's own inline function judged once per call site, with its `line` remapped to the origin line and the origin class carried as `inlined_from_class_name`. Coroutine machinery is recognised by instruction shape, matched by suffix because the shaded jar rewrites `kotlin/` literals, and only inside a suspend-shaped method (a trailing `Continuation` parameter, or `invokeSuspend` on a `kotlin.coroutines.jvm.internal` subclass). Dropped sites keep their place in the site numbering, so `branch_index` names a site in the bytecode and does not shift when the scope configuration or a later drop rule changes what is probed; only the slot layout, and so the layout hash, changes.

## Considered options

- Keeping the probes and marking them, as ADR 0022 does for inline functions. Rejected: 0022 kept the probe because a call from Java or through a reference still lands on it, so the counter carries evidence. A library branch copied into the adopter's method and a switch case that cannot execute carry none, so a marked probe is a slot, a manifest entry and a wire field spent on a value nobody can use. Dropping needs no wire vocabulary and no consumer change.
- Dropping every non-identity SMAP range, which is what JaCoCo's `KotlinInlineFilter` does. Rejected: the adopter's own inline function would then be judged nowhere, since its own probe is already marked inline and every copy would be gone. Keying on the origin class's scope is the rule call edges already use.
- Excluding suspend methods from the branch tier entirely. Rejected: the adopter's own `if` inside a handler is exactly what the tier is for, and it sits in the same method as the machinery.

## Consequences

- The rewriter allocates slots in encounter order and does not consume the analyser's site list, so the analyser hands it the per-method ordinals of dropped sites and the rewriter emits those sites unchanged without allocating. The existing site-count mismatch check is unchanged.
- With debug info stripped there is no SMAP: nothing is recognised as a copy, and inlined code is attributed to the caller as it was before this decision. Coroutine recognition does not depend on debug info.
- The dropped count per class is logged at FINE, and the export scheduler logs one total at INFO on the first flush, so an adopter can see the rule working without a wire field.
- A suspend function's continuation class (`Foo$bar$1 extends ContinuationImpl`, one per suspend function with a suspension point; `RestrictedContinuationImpl` for restricted suspension) holds no adopter code: its `invokeSuspend` only runs on resumption after a real suspension, so on a function that never suspends it reads as never hit and, as a body class under ADR 0024, roots a false unreached cluster. The class is not synthetic. It is excluded from the type matcher and the static scanner through `TypeMatchPolicy`, by direct superclass matched by suffix, so it has no probes, no edges and no declaration. The check reads the superclass's name only, which a lazily resolving pool (`TypePool.Default.WithLazyResolution`, ByteBuddy's `AgentBuilder` default, and what the scanner builds for every root) answers even when no locator can find the stdlib, the fat-jar case; under an eager pool the erasure lookup throws and is caught as "not a continuation". A suspend lambda's class extends `SuspendLambda` and holds the adopter's body, so it stays probed. Confirmed with `javap` on Kotlin 2.2.21 output.
- Amended on 2026-09-26, from the shapes demo run against the stack. The compare against the suspended marker also comes in a stack form, `dup; invokestatic IntrinsicsKt.getCOROUTINE_SUSPENDED; if_acmpne`, which never stores the marker to a local, so the local-slot shape does not match it. kotlinc emits it for the debug-probe hook in an expansion of `suspendCoroutineUninterceptedOrReturn` (so for every inlined `suspendCoroutine`), and for the return of a suspend call in tail position of a function returning `Unit`. Those three instructions in a row are machinery inside a suspend-shaped method; the `dup` keeps an adopter's own `x === COROUTINE_SUSPENDED`, which loads `x` instead. Confirmed with `javap` on Kotlin 2.2.21 output of the shapes demo's `handOff`, and with JaCoCo 0.8.13's offline instrumenter, which leaves the three adjacent.
- Amended on 2026-09-26: a suspend lambda's class (direct superclass `SuspendLambda` or `RestrictedSuspendLambda`, by suffix) keeps its probes on `invokeSuspend`, which holds the body, but its non-static, non-bridge `create` and `invoke` get none, are not declared by the static baseline, and pass through when called, the way ADR 0047 treats an enhancement method. kotlinc writes both, and which one runs depends on how a library starts the lambda, not on the adopter's code: a start through `createCoroutineUnintercepted` calls `create` and never `invoke` (`startCoroutine`, `sequence`, kotlinx `launch` and `async`, `withContext` onto another dispatcher), while a direct call, `startCoroutineUninterceptedOrReturn` and kotlinx's undispatched starts (`coroutineScope`, `withContext` on the same dispatcher) call `invoke`, which calls `create`. Read in kotlin-stdlib 2.2.21's `IntrinsicsJvm.kt`, kotlinx-coroutines 1.9.0's `withContext` bytecode, and the lambdas' own bytecode. So `invoke` read as never hit on every lambda a library started through `create`, and `create`'s count only repeats `invokeSuspend`'s. A lambda with two or more parameters has no `create` and is always started through `invoke`. Leaving `create` probed and dropping only `invoke` was set aside: it keeps a node that says nothing `invokeSuspend` does not. Marking them with a `GeneratedBy` value was rejected as a change in three repos to hide rows that carry nothing; if the lambda never ran, `invokeSuspend` says so. Recognition is by name and superclass, not by body: nobody adds a method to a Kotlin lambda, and `SuspendLambda` is `internal` to the stdlib.
- The four coroutine shapes must each be confirmed against `javap` output before they are coded, and the recogniser must accept the inverted jumps JaCoCo's offline instrumenter leaves, pinned by the same test the omission tier uses.
- A same-class inline function's copies carry the class's own name as `inlined_from_class_name`, since the fact stated is "copied from an inline body", not "from another class".
- Sites that are true but uninteresting (the null path of a safe call, a `!!` check, a `finally` copy on the exception path) are not covered. They are conditionals the adopter wrote, and telling them from dead code is the collector's classification job under ADR 0015.
- Amended on 2026-10-03 by ADR 0052: the shapes this record reads are read from the class file, not the received bytes, so an earlier transformer such as JaCoCo leaves them unchanged.

## Amended on 2026-10-03: machinery the agent cannot read

A jump or switch in a suspend-shaped method that is fed by `getfield label` on a continuation class or by the `getCOROUTINE_SUSPENDED` value, and matches none of the shapes above, was kept as an ordinary site. It is an unread shape of family `COROUTINE_MACHINERY` (ADR 0054): probed, counted, and never a finding. All four shapes, both compare forms and the continuation class were identical from kotlinc 1.9.25 to 2.4.20; a suspend lambda's `invokeSuspend` reloads its parameter per state below language version 2.2, which leaves the machinery shapes intact.
