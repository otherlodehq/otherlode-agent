# A plain servlet is counted at its own entry against its matched mapping

Decided on 2026-10-18 in a grill on the servlet module. A plain servlet application reported no endpoints, and ADR 0072 found no marker class that tells it apart from Spring's `DispatcherServlet` or Jersey's `ServletContainer`. The servlet API gives no point where registration is final: the spec says `ServletRegistration.addMapping` throws once a context is initialised, but Tomcat 9 and 11 (`ApplicationServletRegistration.addMapping`, live through `MapperListener`), Jetty (`ServletHandler.addServletWithMapping`) and Undertow 2.3 (`DeploymentImpl.tryAddServletMappings`) all accept a mapping after start, and no portable hook marks a context as started.

- **One `servlet` module for `javax.servlet` and `jakarta.servlet`**, compiled against `javax.servlet-api` 4.0.1 and rebound to `jakarta.servlet` where the woven method takes that namespace, as the Spring MVC module does.
- **Servlet 4.0 is the floor.** A request is counted against `HttpServletRequest.getHttpServletMapping()`, which Tomcat 9, Jetty 10 and Undertow 2.0 are the first to implement. On an older servlet API the call fails to link and the module disables itself with `LINKAGE_ERROR`.
- **Counted at the servlet's entry, for a `REQUEST` dispatch only.** A filter that answers first leaves the request uncounted, as it does for the Spring MVC module. A `FORWARD`, `INCLUDE`, `ASYNC` or `ERROR` dispatch counts nothing: a request counts once, and an error page is not a call.
- **Declared at a context's first request**, from `getServletRegistrations()`. The module holds the context weakly and reads its registrations again at each flush, so a mapping added late is declared within one flush interval. A context that never receives a request declares nothing, as a Vert.x router does (ADR 0073). The first request is the first `REQUEST` dispatch of any hooked servlet in it, one that is left out included.
- **Verbs come from the `do*` methods the servlet's class declares** below `HttpServlet`, read from the class file. `HttpServlet.doOptions` reads `doGet`, `doPost`, `doPut` and `doDelete` the same way for its `Allow`, but always allows `OPTIONS` and `TRACE` and never reads `doHead`. `doGet` declares `GET`, and a `HEAD` counts against it unless the class declares `doHead`. `doPost`, `doPut` and `doDelete` declare their verbs. `doPatch` declares `PATCH` only on Servlet 6.1, since `HttpServlet.service` answers `PATCH` with 501 before 6.1. `doOptions` and `doTrace` declare a verb only when the class declares them. A class that overrides `service`, or a servlet that is not an `HttpServlet`, has the verb `*`. A request whose verb the servlet does not declare counts nothing. The handler is the `do*` method, or `service` for a `*` servlet. A `do*` that only calls `super` reads as served, as it does for `doOptions`.
- **Exact and path mappings are path templates**, and the context root `""` is `/`. **An extension mapping (`*.do`) and the default mapping (`/`) are servlet pattern templates**, kept exactly as written under a third `EndpointTemplateKind`, since no path template matches at any depth or matches only what nothing else did. The server accepts the kind before an agent sends it.
- **The context path is left out of the template**, as Spring, WebFlux and JAX-RS leave theirs out. Two applications in one container that map the same pattern merge, by the identity rule.
- **An owned servlet is left out**, whatever its module's state: `DispatcherServlet` and its subclasses (Grails' among them) for Spring MVC; Jersey's `ServletContainer`, RESTEasy's `HttpServletDispatcher` and `HttpServlet30Dispatcher`, and CXF's `CXFServlet` and `CXFNonSpringJaxrsServlet` for JAX-RS; `DefaultMicronautServlet` for Micronaut; Ktor's `ServletApplicationEngine` in both namespaces; Javalin 6 and 7's `JavalinServlet`. A framework servlet no module counts behind, such as Vaadin's, JSF's `FacesServlet`, Spring WS's `MessageDispatcherServlet` or the H2 console, is a plain servlet.
- **The container's own servlets are left out by exact class name**: Tomcat's `DefaultServlet` and `JspServlet` (which serves `<jsp-file>` registrations too), Jetty's `DefaultServlet` in each of its packages, `JettyJspServlet` and `ServletHandler$Default404Servlet`, Undertow's `DefaultServlet`, and Quarkus's `QuarkusErrorServlet`. An adopter's subclass of one is the adopter's code and is counted. A container not on the list has its default servlet counted as a servlet at `/`, which is noise, never absence.
- **A mapping outside the spec's five forms disables the module.** Jetty accepts regex and URI-template path specs as servlet mappings. A registration holding one disables the module with `ROUTE_WALK_FAILED`, and a `REQUEST` dispatch to a declared servlet whose mapping has no match type disables it with `ADVICE_FAILED`.

Proved on Tomcat 9.0, 10.1 and 11, Jetty 10 and 12 (ee10), and Undertow 2.3, with Jetty 9.4 showing the `LINKAGE_ERROR` floor and a Spring Boot embedded Tomcat showing `dispatcherServlet` left out, the H2 console counted, and no request counted by two modules.

## Considered options

- **Counting where the container matches the mapping, before the filters.** Rejected: it needs version-sensitive internal hooks in Tomcat's `Mapper`, Jetty's `ServletHandler` and Undertow's `ServletPathMatches`, against one portable hook with the Spring module's semantics.
- **Declaring from per-container "started" hooks** (`StandardContext.startInternal`, `ServletHandler.initialize`, `DeploymentManagerImpl.deploy`). Rejected: three internal hooks that still miss a mapping added after start.
- **`*` for every mapping**, as the JDK `HttpServer` module does. Rejected: a verb nobody sends to a live mapping could never show as never called.
- **Counting a single-mapping servlet on a container older than Servlet 4.0**, or re-running the spec's path matching. Rejected: the first counts part of an application, which is worse than a disabled module, and the second guesses at container matching rules.
- **Counting an owned servlet while its module is off.** Rejected: a Spring application would report one `* /` endpoint taking every hit, hiding the disabled module behind a busy endpoint.
- **Counting `CXFServlet` as a servlet.** Rejected: its JAX-RS requests would count under two identities. Its SOAP traffic goes uncounted and is listed as not covered.
- **Extension and default mappings as regex templates, squeezed into the path grammar, or left out.** Rejected: `*.do` is not a regular expression, `/*` would merge the default mapping with a real `/*` mapping, and leaving them out hides servlets that serve.
- **Counting JSP pages.** Deferred: each page runs inside the container's one JSP servlet, so counting a page needs a hook in the JSP engine.

## Amended on 2026-10-18: what the containers showed

- **A late `ServletRegistration.addMapping` is refused by most containers.** Tomcat 9.0.123, 10.1.61 and 11.0.27 throw `IllegalStateException` from `ApplicationServletRegistration.addMapping` once the context is initialised (message key `applicationServletRegistration.ise`, absent in 9.0.83, 10.1.46 and 11.0.24), and so does Jetty 10.0.26 ("Started"). Jetty 12.0.40 (`ee10`) and Undertow 2.3.26 accept it. A mapping can still arrive after start through container internals: Tomcat's `Context.addServletMappingDecoded` and Jetty's `ServletHandler.addServletWithMapping`. Such a mapping is counted from the flush after it was added, since only the flush reads registrations again. The late-mapping test adds one by each container's own means.
- **Jetty does not accept a regex or URI-template spec as a servlet mapping.** `ServletHandler.asPathSpec` builds a `ServletPathSpec` for every mapping in Jetty 9.4.58, 10.0.26 and 12.0.40 (`org.eclipse.jetty.ee10.servlet.ServletHandler`), and its constructor throws `IllegalArgumentException` ("Servlet Spec 12.2 violation") for anything else. A regex mapping reaches a registration only through a `ServletHandler` that overrides `asPathSpec`. The rule holds unchanged: a mapping outside the five forms disables the module with `ROUTE_WALK_FAILED`, tested through such a handler.
- **One hook per request.** The advice is woven onto every public `service(ServletRequest, ServletResponse)` a servlet class declares, `HttpServlet`'s own included, and a servlet's keys are bound only for the most derived class that declares it. A `service` that calls `super.service` passes through several woven frames, and exactly one finds an entry.
- **The advice must verify inside a Servlet 3.1 class file.** The API jar's `HttpServlet` is class file version 51, which cannot call a static interface method. The advice builds its lookup key with `Arrays.asList`, since an inlined `List.of` failed verification of `HttpServlet` on Jetty 9.4 and the application did not start.
- **The container list gains Jetty's `NoJspServlet`**, which Jetty registers as `jsp` when no JSP engine is present, and every Jetty name is matched in the ee11 packages as well as ee8 to ee10.
- **A walk that cannot vouch for a servlet disables the module with `ROUTE_WALK_FAILED`**: a servlet class whose class file cannot be read, a registration with no class name, or any throw while a context's registrations are read. The five-form check applies only to servlets the module counts, so an owned or container servlet with an unusual mapping disables nothing.

## Amended on 2026-10-18: what review of the module found

- **A request whose mapping has no match type disables the module before anything is declared.** The Servlet 4.0 API's default `getHttpServletMapping` answers with an empty servlet name, an empty pattern and no match type. A 4.0 API jar over a container that does not implement it, which is what `spring-boot-starter-jetty` 2.7 puts on Jetty 9.4, links, so the call never failed: the module declared every mapping and counted none of them, and plain servlets read as dead. A `REQUEST` dispatch whose mapping has a null match type now switches the module off at once. The kind is `LINKAGE_ERROR` when the name and the pattern are both empty, which is the API's default and says the container does not implement Servlet 4.0, the same cause as a 3.1 jar that does not link. A filter that hands the servlet a request object which does not delegate `getHttpServletMapping` shows the same default and gets the same kind. Any other null match type is `ADVICE_FAILED`: an implementation or a wrapper that hides the match. Tested on Jetty 9.4.58 with `javax.servlet-api` 4.0.1 in place of Jetty's 3.1 jar, and on a request object that does not extend the wrapper.
- **A request counts in the servlet the container matched.** A servlet that calls another servlet's `service` directly enters a second hooked frame with the first servlet's mapping, and built the same key. The hook counts only when the `ServletConfig` of the servlet it runs on names a servlet other than the matched one. The `super.service` chain is one instance and one name, so it still counts in exactly one frame by the entry class. A servlet with no config, or a config with no name, counts, since leaving it out would hide a servlet that serves. A servlet called directly before the container initialised it still counts a second time. Rejected: a thread-local call depth or a request attribute, which are a seam change or state the application can see.
- **An owned servlet is left out only where its module covers the release.** Javalin 5 and Ktor 1 ship the class names of Javalin 6 and 7 (`io.javalin.http.servlet.JavalinServlet`) and Ktor 2 and 3 (`io.ktor.server.servlet.ServletApplicationEngine`) and have no module, and a Javalin 5 WAR loads no `javalin-5` marker, so their traffic went unreported. The class loader now has to hold a class only the covered releases ship: `io/javalin/router/ParsedEndpoint.class` (Javalin 6.0.1 to 7.2.3 have it, 4.6.8 and 5.0.0 to 5.6.5 do not) and `io/ktor/server/routing/Route.class` (ktor-server-core 2.3.13 and 3.0.3 to 3.6.0 have it, 1.6.8 has `io/ktor/routing/Route.class` instead). It is read as a resource when the servlet's class file is read, so the answer is held with the shape, per class loader. Without the class the servlet is a plain servlet. The other names stay unconditional, since a release that has the class is either counted or reported: Micronaut 2's `DefaultMicronautServlet` (micronaut-servlet 1.0.2 and 2.1.4 ship it) meets a router the `micronaut-3` module matches and servlet and Netty dispatch methods it does not (`handleRouteMatch` takes four arguments in 2.5.13, `invokeRouteMatch` five), so the module's unmatched-hook check reports it switched off with `HOOK_UNMATCHED` and the servlet stays visible as a disabled module. That path was read from the module's matchers and the two jars' signatures, not run against Micronaut 2. Jersey, RESTEasy and CXF servlets host resource classes the JAX-RS module reads by annotation on any release, and Spring's hooks either match or switch the module off the same way.
- **An exact or path mapping is a path template only when the shared normaliser leaves its meaning intact.** Containers match an exact mapping literally, and Tomcat accepts `/api*` and `/a{b}` with a log line, so refusing them switched the module off for a legal application, and reading `/a/` as `/a` merged two mappings. A mapping that starts with a slash is a path template when `RouteTemplateNormalizer` returns it unchanged and no star or brace stands before a final `/*`. Any other mapping that starts with a slash (a trailing slash, doubled slashes, a whole-segment `**` or `<name>`, a star or a brace) is a servlet pattern template, kept as written. An extension mapping needs only a non-empty text without a slash after `*.`. Only a mapping that does not start with `/` or `*.`, and is not the empty string, is outside the five forms. Jetty's URI template spec `/a/{id}` is indistinguishable from an exact mapping that holds braces and reads as one; its regex spec still switches the module off.
- **The context is declared before the lookups, not after the first miss.** Declaring on a miss made a request to an owned servlet, which always misses, run four lookups and a declare. The hook calls `declare` first, which does nothing for a held context (a volatile read and a short array scan, no lock), then looks up the verb and `*` keys: an owned servlet now costs a declare and two lookups, and a counted servlet a declare and one or two lookups. The words match the code: a context is declared at the first `REQUEST` dispatch of any hooked servlet in it, so a context whose only traffic reaches `DispatcherServlet` still declares its plain servlets as never called.
- **The verb rule is `doOptions`' reading of four methods only.** `HttpServlet.doOptions` allows `GET`, `POST`, `PUT` and `DELETE` by the methods a class declares, always allows `OPTIONS` and `TRACE`, and never reads `doHead`. The module declares `HEAD`, `OPTIONS` and `TRACE` only for a class that declares them, which is a rule of its own.
- **Undertow implements `getHttpServletMapping` from 2.0.0.Final.** The record named 2.0.42; `HttpServletRequestImpl` of 2.0.0.Beta1 has it and 2.0.0.Alpha1 does not.
- **An asynchronous dispatch is tested**: a servlet that calls `startAsync` and then `dispatch` counts once, on every container.

## Amended on 2026-10-20: a servlet whose superclass cannot be read is no match

- **The type matcher asks the class's loader for a supertype the pool cannot describe**, by the rule ADR 0017 sets for JAX-RS and with the same code (`SupertypeResolver` in `endpoints-api`). The agent's pool resolves lazily, so `hasSuperType(Servlet)` threw for a class declaring a public `service(ServletRequest, ServletResponse)` whose superclass has no class file, and the throw switched the whole module off as `TRANSFORM_FAILED`. A supertype that does not load means the class can never be defined, so it is no match and the module stays on. One that loads without a reachable class file is read from the loaded class and counts if it is a servlet. A loaded supertype whose methods cannot be reflected still reaches the matcher's catch. The declare-time class-file walk reads class files by resource, so a registered servlet whose superclass is defined in memory disables the module with `ROUTE_WALK_FAILED`.

## Amended on 2026-10-26: a class file without a service descriptor is not parsed

- **The module rejects a class from its raw bytes before the pool parses it.** The module's loader gate passes any loader that can see a servlet API, which in a Spring Boot fat jar is the loader of every Spring, Tomcat and application class. The type matcher's first checks, `not(isInterface())` and `declaresMethod`, made the pool parse every one of those class files. On PetClinic pinned to one core, that cost about 0.4 s of startup, measured locally with nine interleaved runs per variant: the module with its type matcher replaced by `none()` started in 10.83 s against 11.22 s, and the supertype walk after `declaresMethod` cost nothing measurable. `EndpointModule.classFileMayMatch` takes the bytes being transformed, and the pipeline asks it after the loader gate and before the type matcher. The servlet module answers whether the bytes hold `/servlet/ServletResponse;)`. Every method `service(ServletRequest, ServletResponse)` has a descriptor that ends its arguments with that text, in a constant pool entry, for both namespaces and any return type. The pool parses the same bytes the check reads, so the check rejects only classes the type matcher would reject. Measured the same way, ten runs per variant: 10.89 s with the check, 11.25 s without it and 10.74 s with the module off, against 8.69 s with no agent. The 0.15 s left is the module's loader gate and installation.
- **The bytes reach the matcher through the transformer.** The pipeline's transformer is wrapped so that the bytes of the class being transformed, with its internal name, are held for the thread while it runs. A matcher call for another class, or outside a transform, gets no bytes and runs the full type matcher.
- **Considered and rejected.** Checking supertypes before methods: the walk is not the cost. A name check, as the other modules use: a servlet can have any name. Turning the module off by default: plain servlets would go unreported.
