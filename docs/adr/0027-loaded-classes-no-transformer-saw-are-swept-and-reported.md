# Classes that loaded but reached no transformer are found by a sweep and reported as unreported

Every other way this agent learns about a class runs from a transformer. There are classes no transformer is ever offered. `java.lang.instrument` refuses to call a transformer while that thread is already inside another transform on the same `Instrumentation`, so a class loaded from inside a transform is handed to none of them: not ByteBuddy's, and not the `ClassBytesCapture` registered ahead of it. `DeflectedClassLoadTest` pins that behaviour. Such a class is defined, runs, and appears in no manifest, as neither a probed class nor a skipped one. A complete static baseline that declared it then has no mention of it anywhere, and a collector calls it never loaded when it loaded and ran. That is the outcome ADR 0007 exists to rule out.

`Instrumentation.getAllLoadedClasses()` is the only thing that sees these classes, so the agent sweeps it. A class in scope that the registry has never heard of, as registered, skipped, or having nothing to probe, is an **unreported class**: it travels on `ProbeManifest` with its name and the time a sweep first found it, and a collector counts it as loaded, which is all it takes for the false claim to stop.

## Considered options

- Recording it from a transformer registered ahead of ByteBuddy's, the way the class-bytes capture already is. Rejected: it does not work, and the test says why. The refusal is per `Instrumentation` and per thread, not per transformer, so every transformer this agent registers is refused together. A second `-javaagent` holds its own token and would be offered the class, which is no help to an agent that is only itself.
- Retransforming the class to instrument it after the fact, rather than only reporting it. Rejected for the method tier by ADR 0013: retransformation cannot add fields, and the probe array field is one. The endpoint tier only weaves advice into existing bodies and may be eligible, which is its own decision and not this one.
- Checking the other direction too, registered but never loaded, which would catch a class the verifier rejected after `onTransformation` had already committed its probes. Deferred, not rejected. The direction this decision takes is race-free by construction: registration commits before `getBytes()` returns and the JVM defines the class only after that, so a class cannot be loaded before it is registered. The reverse direction has no such property, and needs a grace period for a class defined moments ago and an answer for a class whose loader has since been collected. `STATUS.md` carries it.
- A log line rather than a wire field, as ADR 0025 chose for dropped branch sites. Rejected: a dropped branch site makes no claim, so an adopter reading a log is enough. Here a collector is already making a claim and getting it wrong, and only the wire changes that.

## Consequences

- Identity is the class name alone, matching `skipped_classes` and every table the collector joins on. A class reported under one classloader and deflected under another therefore reads as accounted for. The registry knows both, since its key carries a classloader identity, but nothing downstream has a concept of one.
- No reason field. A class the agent turned away on purpose carries a reason, and this bucket is what is left after those are accounted for, so the only honest reason is one it does not have.
- The sweep runs every tenth flush and always on the shutdown flush, not on every flush. The finding has no expiry, a class that loaded unreported stays unreported, while the walk allocates an array of every class the JVM holds. The interval is a constant rather than an option: tuning it needs the cost on a particular application, which an adopter cannot see.
- A class the agent looked at and found nothing in to probe, a marker interface or a constants holder, is recorded locally so the sweep can tell it apart from a genuine blind spot. That record never reaches the wire, because nothing claims anything about such a class: the static scanner puts its own copy in the baseline's unprobed bucket rather than declaring it. It is recorded only when the class's bytes were readable. Without them every analysis answer is empty whatever the class holds, and a Scala class whose lambda bodies are its only probe-worthy methods reads as empty too, since the Scala marker comes from those same bytes. Recording that as nothing to probe would tell the sweep the class is accounted for and hide the one case its own warning exists to report, which is the wrong way to fail.
- ByteBuddy applies its own ignore matcher before any `.type(...)` matcher runs, so the sweep has to replicate that gate as well as the type matcher. A class on the bootstrap or platform loader, or named under ByteBuddy's own package or the reflection internals, reaches no transform callback and is not a blind spot. Leaving that out made the sweep report the whole JDK the moment `includePackages` was left at its default, since an empty include list means "everything outside the agent's own package" and it is ByteBuddy's gate, not the type matcher, that supplies "outside the JDK". Array classes and hidden classes are dropped for the same reason; a hidden class also carries a `/0x...` suffix in its name that could never join to anything a collector holds.
- The scope filter runs three of the type matcher's four checks against the loaded class: the name rules, the synthetic flag, and the coroutine-continuation check, which reads only the direct superclass's name. The fourth is left out on purpose. Reading a class's annotations resolves each annotation's own type and can load classes, and a sweep must not load anything in order to look; a class turned away for an illegal annotation is recorded as skipped anyway, so it never reaches the filter.
- The sweep is not gated on `staticBaselineEnabled`, though the claim it defends only exists when that is on. The flag is per instance and the claim is fleet-wide, so an instance with the scan off still contributes to what the collector knows loaded.
