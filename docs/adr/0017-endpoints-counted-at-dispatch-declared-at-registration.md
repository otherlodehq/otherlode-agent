# Endpoints are counted at the framework's dispatch point and declared by its registration hooks

The method tier can say a handler method ran, but not that `GET /promo` was ever served: a handler may back two endpoints, be a lambda the framework invokes through a hidden class, or live outside `includePackages`. Endpoints therefore get their own probe. An endpoint probe counts one endpoint, identified by verb and normalised route template, and is incremented at the point where the framework has matched a request to that endpoint, before the handler runs. The declared list of endpoints comes from the same framework's registration hooks (Spring's handler-method mapping, Ktor's `handle`, `HttpServer.createContext`), plus transform-time annotation reading for JAX-RS, which has no registration API. This is the same technique OpenTelemetry's agent uses to produce `http.route`, extended with a declared list, which OpenTelemetry never needs because a span nobody creates is not a gap.

The handler join (which manifest method backs an endpoint) is a label on the endpoint record, recorded at registration where the framework hands over a method and at first dispatch otherwise. It is never a second counter and never a field on the method probe's own record.

## Considered options

- Attribution only: no new counter, method probes gain a route label. Rejected: the endpoint claim would depend on whether the method tier happened to catch the handler, which fails for Java lambdas (hidden classes), handlers in excluded packages, and one method serving two endpoints.
- OpenAPI as the source of endpoints. Set aside: a document gives an inventory and labels, not a join, and is scarce exactly where annotations are absent. It remains a candidate for a separate contract-diff feature.
- Static analysis of registration call sites (`LDC "/path"` followed by an `invokedynamic` naming the handler). Set aside: fragile on computed paths and nested prefixes, which registration hooks handle for free.
- Reading `http.route` off the current OpenTelemetry span. Rejected for v1: it couples correctness to the OpenTelemetry version on the bootstrap path and to its source-priority rules, and gives no declared list. Both agents coexist since each only reads framework state.
- Muzzle-style reference checking per framework version, as OpenTelemetry does across its two hundred modules. Rejected at seven modules: each module compiles against its oldest supported version, is never shaded, and disables itself once with a warning on the first `LinkageError`, reporting that on the wire.

## Consequences

- Framework classes are matched by a second matcher path, gated on the framework class being present on the loader, untouched by `includePackages` and `excludePackages`, which describe the adopter's code. One switch, `endpointsEnabled`, on by default.
- A hit means "matched", not "completed" or "2xx". A handler that throws still ran. Requests matching no endpoint are not counted.
- Identity is `(verb, normalised route template)` and nothing else, so two servers in one JVM serving the same template merge, and JAX-RS identity excludes `@ApplicationPath`, which is not known when the resource class transforms. The framework's own spelling is kept beside the identity for display.
- A dispatch for an endpoint no registration saw creates the entry lazily, marked as discovered by dispatch, so the hit is never dropped.
- Every endpoint the framework serves is reported, including Actuator and static-resource handlers. Narrowing to the adopter's code is a collector-side filter on the handler class.
- Advice reaches the registry through a seam in the bootstrap module, as in 0004, with a bounded replay buffer for registrations that arrive before the resolver is installed, and a module read edge added for `jdk.httpserver`. Any helper that touches a framework is Java and never names a `kotlin.*` type, since the shaded jar relocates the Kotlin standard library and would rewrite such a reference to a class the framework does not have.
- The wire change is additive on `ProbeManifest` and `DeltaBatch`. Endpoint records carry a "changed since delivered" state so a join learned after delivery is re-sent; class records stay send-once.
- A framework whose declared routes are only reachable by walking one of its objects with a visitor (Spring's `RouterFunction`) is declared through a second seam call, `declare(module, frameworkObject)`, woven where the framework finishes building that object. The seam hands the object to the module's own code on the agent loader, which walks it reflectively, since advice can neither define a visitor class nor call a helper. Dispatch-only discovery for such routes was rejected: it would forfeit "never called" for the one Spring style whose handlers are lambdas, where the method tier is weakest.
- Every URL-mapped handler mapping (`AbstractUrlHandlerMapping` and its subclasses, including Boot's static-resource mappings) is declared and counted with verb `*`, since those mappings carry no verb.
- A module whose route walk throws is switched off the same way an advice failure switches it off: dispatch stops counting and the module is reported disabled. A walk that failed partway has an incomplete declared list, and counting against it would let a collector call an endpoint never called when it merely went undeclared. No data for that framework is the safer report than partial data.
- The JDK `HttpServer`, Ktor, and Spring functional-route modules join a handler the same way the annotation-mapped and JAX-RS modules already do: when the handler object's class is not hidden (`Class.isHidden()` false), the join names the method the framework actually invokes on it (`handle` for `HttpServer` and Spring functional, `invokeSuspend` for a Ktor suspend lambda) and the class that declares that method, so an inherited method joins to the base class where the probe lives, not to the subclass. A hidden class, generated for a Java or Kotlin SAM-converted lambda through `invokedynamic`, has no stable name across runs, so its class, method, and descriptor are all reported as null instead, matching the annotation-mapped side's own no-join rule for a Java lambda. `OtherlodeEndpoints.attachHandler` and `register` are both no-ops for a null handler class, so passing null for a hidden class can never overwrite a real join a different registration or dispatch point already recorded. ADR 0035 names a hidden handler from the JDK's lambda factory where it can, starting with the JDK `HttpServer` module. Null stays the answer when nothing was recorded.
- Settled in a review on 2026-10-03, each after a failing test. Spring's annotation join names the class declaring the method, so a mapping inherited from a base controller joins where its probe lives. A request several patterns of one mapping match counts Spring's best match, read from the condition's sorted set, not from `getPatternValues()`, which is a hash set. A URL-mapped request no registered path matches counts against `/*`, not one endpoint per URL. Handler methods registered through `registerMapping`, as Spring Boot Actuator registers every operation, are declared too. A functional route with no path of its own inside a nest is declared at the nest's path, and a CORS preflight is no call of the route it asks about. Ktor's dispatch advice ignores the null-argument re-entries of its suspend dispatch method. A non-value dispatch key (a route node, an `HttpContext`, a `HandlerFunction`) is held weakly and compared by identity, so a discarded routing tree is not kept alive by the registry. The route normaliser keeps every parameter and the literal text between them in a segment.
- Amended 2026-10-05 from the startup measurements: a module may reject a class loader before any class on it is parsed (`EndpointModule.classLoaderMatcher`, which the pipeline asks before the type matcher). JAX-RS, the one module that reads every loaded class's annotations, accepts only a loader that sees `jakarta/ws/rs/Path.class` or `javax/ws/rs/Path.class` as a resource, looked up once per loader, and never the bootstrap or platform loader. A class whose loader cannot see the API cannot carry an annotation a JAX-RS runtime could read, so nothing is lost; on an application without JAX-RS this took about 1.5 s off startup. Its supertype walk caches each supertype's answer per loader. The include and exclude rules still do not apply.

## Amended on 2026-10-07: a hook that matches no method switches its module off

Decided in the grill on the customer docs round's follow-ups. ByteBuddy attaches `Advice.on(matcher)` to every declared method the matcher accepts and to nothing else: with no match it writes the class unchanged, throws nothing, and the transformation reports success (`AsmVisitorWrapper.ForDeclaredMethods`, byte-buddy 1.18.12). So without a check, a framework release that renames a hooked method, or changes its parameter count, leaves the module silent. A lost registration hook reports no endpoints for the framework. A lost dispatch hook is worse: registration still declares every route, and every one of them reads as never called.

Each hook a module attaches is checked when its class is woven. A module attaches a hook through an `AdviceBinder` method that takes the hook's method matcher with its advice and records the matcher. The binder is cached per loader and shared across threads, so the pipeline hands each module's `transform` call a fresh view of it that holds the record for that call alone: classes woven in parallel, and two modules matching one class, never share a record, and a re-weave's view is discarded unread. After the module's `transform` returns, the pipeline counts the class's declared methods that each hook's matcher accepts and that are neither abstract nor native, the methods `Advice` can weave. A hook with none switches the whole module off, as a linkage failure does, since no data for a framework is the safer report than partial data. The disable is committed with the class's transformation and dropped if the transform fails, the way declarations are, and a re-weave (ADR 0053) checks nothing. A framework module matches its framework classes by exact name and shape, so a hooked method is declared on the class that is checked, never inherited into it. Shape matters across major releases that reuse a name: Ktor 3 turned Ktor 2's `Route` and `Routing` classes into interfaces, whose `handle` is abstract and which declare no `executeResult`, so the Ktor 2 module matches those names only as classes, and on a Ktor 3 application it matches nothing rather than reporting a hook unmatched. The JAX-RS module builds each hook's matcher from the methods it has just read off the adopter's class, so its hooks always match. The verdict is complete when the class is woven, so no "end of startup" is needed: a framework class that loads late is judged when it loads.

`DisabledEndpointModule` gains `kind`, an additive enum, beside the free-text `reason`:

- `LINKAGE_ERROR`: a `LinkageError` wherever it was caught. The framework release differs from the one the module was built for.
- `ADVICE_FAILED`: any other throw from the module's advice.
- `TRANSFORM_FAILED`: the module's `transform` threw, or ByteBuddy failed to weave a class the module matched. A failed weave leaves a module that hooks framework classes without the hooks the weave would have added, so every module whose matcher accepted the class is switched off; the pipeline records them per thread for the class being woven, a matcher that throws included, and clears the record when the class is done. JAX-RS is the exception: a resource class whose weave fails takes its own staged declarations with it, so nothing partial is left, and the module stays on. A failure on a re-weave switches nothing off, since the JVM keeps the bytes the first weave produced.
- `ROUTE_WALK_FAILED`: a route walk threw (the bullet above on `RouterFunction`).
- `HOOK_UNMATCHED`: a hook matched no method. The reason names the hook's method and the class.

The zero value, `DISABLED_ENDPOINT_MODULE_KIND_UNSPECIFIED`, is what an agent built before `kind` sends. The bootstrap seam's `moduleFailed` takes the kind beside the throwable, since the throwable alone cannot tell a failed route walk from a failed advice.

The testkit exposes `kind`, and the collector's bindings are bumped so its redaction keeps it.

This is a narrow form of the reference checking rejected above: one existence check per hook on a class the pipeline is already weaving, not a model of every reference a module makes. It cannot see a hooked class that was renamed, since the type matcher never matches and that reads exactly as the framework being absent. A scheduled CI job covers that and every other drift: it runs each endpoint module's tests against the newest release of its framework, as the compiler canary does for compilers (ADR 0055), so a release that breaks a module fails a build before it reaches an adopter.

Considered: checking signatures by reflection later, from the sweep or after startup. Rejected: it needs the loaded `Class`, `getDeclaredMethods` resolves parameter types and can load classes or throw, which breaks "reflects as the unwoven class does", and it needs a moment at which the verdict is final. Disabling only the hook that missed was rejected for the partial-data reason above. A free-text reason alone was rejected in favour of the enum, so a consumer never parses text to tell a version drift from a bug.

## Amended on 2026-10-17: a module can be switched off by configuration, and is reported when it is

Decided in a grill on the endpoint follow-ups. `disabledEndpointModules` takes module names separated by `;`, and the agent installs none of the modules it names. A module whose framework misbehaves without throwing never switches itself off, and `endpointsEnabled=false` takes every other framework's endpoints with it. OpenTelemetry's agent gives each instrumentation a switch of its own (`otel.instrumentation.[name].enabled`) for the same reason.

Each module the configuration keeps from installing is sent as a `DisabledEndpointModule` with the kind `CONFIGURED_OFF`, whether or not its framework is present: every module the option names that would otherwise have been installed, and under `endpointsEnabled=false`, every module that would otherwise have been installed. Without it a framework left uninstrumented reads on the wire as one with no endpoints, the gap `endpointsEnabled=false` left by sending nothing. The route bridge counts as installed only when `otelBridgeEnabled` is on. A name that matches no module gets a WARNING listing the known names and is skipped, since it leaves more instrumentation on, never less. The collector's bindings are bumped so its redaction keeps the new kind, and the server words it as the adopter's choice rather than a failure.

Considered:

- Reporting a module only once its framework is seen, by keeping it installed but inert. Rejected: its type matching keeps running, which may be the cost the adopter switched it off to avoid (JAX-RS's annotation reading, in the 2026-10-05 amendment above).
- A field on `ResourceAttributes` listing the modules switched off. Rejected: `DisabledEndpointModule` already tells the server "endpoints not instrumented", and the server joins it to endpoints by module name.
- One boolean per module in OpenTelemetry's shape. Rejected: every other option has a fixed key whose property and variable names derive from it (`OptionNames`), and module names hold dashes an environment variable cannot.

## Amended on 2026-10-17: modules for WebFlux, Javalin, Micronaut and Vert.x, never static analysis

Decided in the same grill. The frameworks with no module (Spring WebFlux, Javalin, Micronaut, Vert.x Web) get runtime modules before 0.1.0. Static analysis of registration call sites stays rejected, now with evidence. Every agent-side declared route list found reads the framework's own route table at runtime, at the point where the framework has finished building it: Datadog's tracer for Spring MVC (`AppSecDispatcherServletInstrumentation`, at `DispatcherServlet.onRefresh`), Spring Boot's `/mappings`, Micronaut's `/routes`, Javalin's route overview and springdoc, whose "build-time" plugins start the application. Static extractors live in source scanners, and where their source is readable they show the weaknesses this record named: OWASP Noir's Vert.x analyser drops a computed path and approximates a sub-router mounted in another file (`vertx.cr:630`, 128-135), and none sees a runtime prefix (`PathMatchConfigurer.addPathPrefix`) or a `${...}` placeholder. All four frameworks expose their route table at runtime.

Each module compiles against its oldest supported release, as the options above say: a module compiled against the newest can use an API an older supported release lacks and fail on it.

Rules every module follows, and the Spring MVC module is brought to:

- **A CORS preflight is no call** of the route it asks about, on every route kind, not only functional routes.
- **A request counts once.** A lookup Spring's `HandlerMappingIntrospector` makes for Spring Security or CORS is no call: it reaches `handleMatch` and `setAttributes` with the request wrapped in the introspector's own `AttributesPreservingRequest`, and under Spring Security 6.1.6 to 6.5 it counted every request twice and counted a request Security rejected before the handler (measured on Spring Boot 3.5.16). An async redispatch is no second call either. The URL-mapped count moves to `AbstractUrlHandlerMapping$PathExposingHandlerInterceptor.preHandle`, which only the `DispatcherServlet` runs, since `buildPathExposingHandler` sees no request to tell the two apart.
- **Functional routes are declared at `RouterFunctionMapping.afterPropertiesSet`**, read from its `routerFunction` field on exit, so a mapping constructed with a router function, as Spring Boot's WebFlux welcome page is, is declared too.
- **A top-level `resources(...)` route is declared and counted**, its pattern read from the resource lookup function by exact class shape, rather than left undeclared and uncounted.
- **An API version is not part of identity** (Spring 7.0), like a header predicate. A request rejected for its version after the route matched counts, since a hit means matched.
- **A handler that resolves to Spring's Kotlin DSL classes** (`RouterFunctionDsl`, `CoRouterFunctionDsl`) gets no join: ADR 0035's rule that a name joining to nothing is worse than none.
- **A WebSocket route whose upgrade never reaches a dispatch hook is not declared**, since every one would read as never called (Micronaut, Javalin). A Spring WebFlux WebSocket handler is mapped by URL and its upgrade passes through `AbstractUrlHandlerMapping.lookupHandler`, so it is declared and counted like any URL-mapped handler.
- **Endpoints a framework adds for itself are declared and counted**, as Actuator's are: Javalin's `HttpAllowedMethodsPlugin` OPTIONS routes and route overview, Micronaut's management endpoints.

Per framework:

- **Spring WebFlux** is a module of its own, `spring-webflux`, so its failure never switches off MVC counting and the option and wire label can name one stack. The two share the functional-route walk, parameterised by package. Hooks are identical in 5.3.39, 6.2.19 and 7.0.9. Reactive URL-mapped handlers count at `AbstractUrlHandlerMapping.lookupHandler` on a non-null return, since the reactive side has no `buildPathExposingHandler` and no root or default fallback. A router run through `RouterFunctions.toHttpHandler` or `toWebHandler`, with no `DispatcherHandler`, is reported by a framework marker (ADR 0072).
- **Javalin** gets `javalin-6` (6.1 and later) and `javalin-7`, each matching `ParsedEndpoint` only by its own release's shape, since the hooked descriptors are the same in both and a module matching by name would weave the other release and fail. Javalin 6.0.x reports a `LINKAGE_ERROR`; Javalin 5 is reported by a framework marker. The true match point is inlined or compiler-generated, so a Javalin endpoint counts at `ParsedEndpoint.handle`, after the before-handlers: a request a before-handler rejects, redirects or skips is not counted, and a Javalin hit means the request reached its handler. A `CrudHandler`'s five endpoints join to its methods by verb and path shape, from a hook on `ApiBuilder.crud` that runs before the inner registrations.
- **Micronaut** gets one module for 4.0 to 5.x, declaring at the exit of `DefaultRouter`'s constructor and counting at `RouteExecutor.findRouteMatch`. Micronaut 3.x, patched again since February 2026, gets a `micronaut-3` module of its own: it registers through the same constructor, but over `UriRoute` rather than `UriRouteInfo`, and it has no `findRouteMatch`, so it counts at the Netty `RoutingInBoundHandler.handleRouteMatch` for a URI route match, with a hook of its own for micronaut-servlet. A HEAD route Micronaut adds beside each `@Get` is not declared, and a HEAD request that matches one counts against the GET endpoint; an explicit `@Head` is its own endpoint. `micronaut.server.context-path` stays in the template, beside the JDK `HttpServer` as an exception, since it is part of the path Micronaut matches and is in annotated routes only.
- **Vert.x Web** has its own record, ADR 0073.

The shared normaliser gains Micronaut's `{/x}` as `/{x?}`, `{x:?}` as `{x?}`, a whole-segment `{+x}` as `*`, and Javalin's whole-segment `<x>` as `*`. A form whose meaning would be a guess (`{.x}`, `{;x}`, `{a,b}`) stays as written, and `{x:.*}` loses its constraint as any regex does. Vert.x's `:name` is converted by its module, since a colon rule in the shared normaliser would break Spring's literal colons (`{name}:cancel`).

## Amended on 2026-10-17: routes are declared only where a counted dispatch point exists

Decided in a grill after the `micronaut-3` review. micronaut-aws 3.x builds its own `RouteExecutor` and reaches neither Netty's `RoutingInBoundHandler` nor micronaut-servlet's `ServletHttpHandler`, so on Lambda every route was declared at `DefaultRouter`'s constructor and none could be counted: every endpoint would read as never called. Every other Micronaut serverless runtime checked (AWS 4 and 5, Azure, GCP, Oracle Cloud, POJA) builds on `ServletHttpHandler` and is counted.

- **`micronaut-3` counts on micronaut-aws 3.x** at the entry of `MicronautLambdaContainerHandler.handleRequest(MicronautAwsProxyRequest, MicronautAwsProxyResponse, Context)`, from the route match the request carries (same descriptor from 3.0.0 to 3.18.0), never its synthetic bridge, which would count twice.
- **A Micronaut module declares a router's routes only once one of its counted dispatch points has been constructed in the process**: Netty's `RoutingInBoundHandler`, `ServletHttpHandler`, `MicronautLambdaContainerHandler`, or 4.x's `RouteExecutor`, in either order. A router no dispatch point ever arms declares nothing, and the module is reported with a disabled kind saying its routes are not counted on this runtime, so the server shows that rather than "no endpoints". A hand-kept list of supported runtimes would fail silently on the next runtime nobody listed.

Considered: gating on a dispatch class being on the classpath. Rejected: a Lambda application that also ships Netty for local runs would still declare what it cannot count.
